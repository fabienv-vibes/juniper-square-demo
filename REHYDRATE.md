# Rehydration runbook — bring up the Juniper Square demo on a fresh workspace

This is the disaster-recovery / new-workspace play. If `fevm-juniper-square-demo`
gets reaped before the extension is approved, this gets the whole demo (catalog,
SDP pipeline, Lakebase syncs, orchestration job, Streamlit app, benchmark results)
back up in under an hour.

## What's captured here

**Code / config (in this repo):**
- `databricks.yml` + `resources/*.yml` — DAB definitions for catalog/schemas/volume,
  SDP pipeline, warehouse, generator job, orchestration job, lakebase-setup job, app
- `data/sdp_pipeline/{bronze,silver,gold}_*.py` — medallion SDP notebooks
- `data/data_gen/generate_gl_spark.py` — 10B-row Spark generator (PySpark, serverless)
- `data/notebooks/lakebase_setup.py` — post-deploy bootstrap for Lakebase
- `data/notebooks/06_lakebase_sync_synced.py` — original TRIGGERED-mode reference
- `data/harness/benchmark_harness.py` — interactive harness notebook (workspace artifact)
- `app/` — Streamlit app (deployed to Databricks Apps)
- `benchmark/benchmark/concurrency_benchmark.py` + `backfill_delta.py` — laptop harness
- `benchmark/results/<ts>/*.csv` — measured benchmark data (5 runs covering all
  sustained scenarios + the original lockstep). Loaded into Delta via `backfill_delta.py`.

**Not captured (and not needed):**
- Silver fact table (1.08 TB) — regenerated by `juniper-data-gen-wider` in ~12 min
- Gold tables (~350 MB) — produced by SDP pipeline (~2 min)
- Mock CSV snapshots used by the app (`app/mock_data/*.csv`) — already in the repo

## Prerequisites for the rehydrate workspace

1. **New FEVM workspace** — request via FEVM CLI/UI, classic, us-east-1, 30-day lifetime.
   Same shape as the original (no Serverless-only constraints).
2. **CLI profile** — add to `~/.databrickscfg`:
   ```
   [juniper-square-fresh]
   host         = https://<NEW-WORKSPACE>.cloud.databricks.com
   auth_type    = databricks-cli
   ```
3. **Authenticate** — `databricks auth login --profile juniper-square-fresh`

## Step-by-step rehydration

### 0. Pre-flight (one-time, manual)

The Lakebase **project** is the only resource the bundle can't create on its own.
Create it via UI before bundle deploy:

- Workspace → Compute → Lakebase → "Create project"
- Name: **`juniper-sq-benchmark`**
- Mode: **Autoscale**
- Min/max CU: **1 / 4**
- Database (default): `databricks_postgres`
- Branch: `production` (default)

Wait for status: READY (≈2 min).

### 1. Deploy the bundle

```bash
cd ~/Projects/juniper-square-repo
databricks bundle validate -t fresh
databricks bundle deploy -t fresh
```

This creates (under profile `juniper-square-fresh`):
- Catalog `juniper_square_demo_catalog` + schemas `raw`, `pipeline`, `serving`
- Volume `raw.landing`
- SQL Warehouse `juniper-benchmark-warehouse` (Medium Pro, 1-8 autoscale)
- SDP pipeline `juniper_benchmark_medallion`
- Jobs: `juniper-data-gen-wider`, `juniper-benchmark-refresh`, `juniper-lakebase-setup`
- App `juniper-benchmark-viewer` (won't start cleanly until warehouse-id patched, see step 5)

### 2. Generate the raw data

```bash
databricks bundle run juniper_data_gen -t fresh
```

≈12 min. Writes 5 dim files + 10B GL rows to `/Volumes/juniper_square_demo_catalog/raw/landing/`.

### 3. Run the medallion + sync stitching

The `juniper-benchmark-refresh` job currently has only the SDP task — sync tasks
are stitched in by `lakebase_setup`. So first run the SDP standalone, then
`lakebase_setup`:

```bash
# Run SDP pipeline directly (orchestration job not yet fully wired)
databricks bundle run sdp_medallion -t fresh
```

≈3-5 min. Populates bronze → silver → gold.

### 4. Bootstrap Lakebase (creates synced tables + wires up the refresh job)

```bash
databricks bundle run lakebase_setup -t fresh
```

≈3-5 min. Creates 4 SNAPSHOT synced tables, waits for ONLINE, captures the per-table
pipeline_ids, and updates `juniper-benchmark-refresh` to fan out to all 4 syncs
after the SDP task.

### 5. Patch the app with the new warehouse id + redeploy

```bash
./scripts/post_deploy.sh juniper-square-fresh
```

This:
- Looks up the new warehouse_id
- Rewrites `app/app.yaml` in place (replaces the hex16 IDs)
- Re-syncs app source + redeploys
- Grants `CAN_USE` on the warehouse to the app's service principal
  (the bundle's `resources:` binding declares the dependency but doesn't grant
   the permission — known gotcha, see memory `accounts/juniper-square.md`)

Then restart the app:
```bash
databricks --profile juniper-square-fresh apps stop juniper-benchmark-viewer
databricks --profile juniper-square-fresh apps start juniper-benchmark-viewer
```

### 6. Restore the benchmark Delta data

The app reads measured benchmark results from
`juniper_square_demo_catalog.pipeline.benchmark_{runs,summary,raw,summary_timeseries}`.
These are populated from the CSVs in `benchmark/results/<ts>/`:

```bash
cd benchmark/benchmark
# Re-generate fresh OAuth tokens for the new workspace
python3 gen_config.py --profile juniper-square-fresh --project juniper-sq-benchmark

# Backfill each run's CSVs into Delta
for ts in 20260424_233045 20260428_150902 20260428_153245 20260428_155553 20260428_162636; do
  python3 backfill_delta.py --config config_live.yaml --results-dir ../results/$ts
done
```

### 7. Verify

- App URL: `https://juniper-benchmark-viewer-<new-workspace-id>.aws.databricksapps.com/`
- Visit `?page=latency` — sustained-rate headlines should populate (118ms / 651ms / 159ms / 859ms tiles)
- Visit `?page=overview` — should show "Redline" placeholder section + Results summary
- Run the orchestration job end-to-end: `databricks bundle run juniper_benchmark_refresh -t fresh`
  (≈5-8 min: SDP medallion + 4 parallel syncs)

## Verifying the bundle today (without deploying)

To confirm the bundle is healthy against the current FEVM:

```bash
cd ~/Projects/juniper-square-repo
databricks bundle validate -t juniper-square-demo
databricks bundle summary -t juniper-square-demo
```

**Do not** `databricks bundle deploy -t juniper-square-demo` against the current
FEVM — the bundle would try to create resources with the same names as ones that
already exist (different owners → conflict). The `juniper-square-demo` target is
documentation-only; `fresh` is the actual deploy path.

If you want DAB to take over management of the *current* resources without
recreating them, use:
```bash
databricks bundle deployment bind <resource_key> <existing_resource_id> -t juniper-square-demo
```
…per resource. Not necessary for the backup-and-rehydrate use case.

## Known gotchas (lifted from memory)

- **App SP grant:** `resources:` block in app.yaml declares a dependency but
  doesn't grant — `post_deploy.sh` handles it. Symptom of missing grant: app
  silently falls back to mock CSV data (preview banner).
- **Synced-table PKs:** `gold_property_financials` requires
  `(arena_id, property_id, month)` — `(property_id, month)` alone causes
  `PRIMARY_KEY_CONSTRAINT_VIOLATION` because 1K properties span 10K arenas.
  Embedded in `lakebase_setup.py`.
- **Streamlit version on Apps runtime:** ~1.30, doesn't support
  `use_container_width=True` on `st.image` — use `use_column_width=True`.
- **`databricks sync` does NOT auto-read `.databricksignore`** — pass
  `--exclude-from .databricksignore` explicitly if running sync manually.
- **DESCRIBE HISTORY fails on Materialized Views** — only works on managed
  Delta tables (e.g. `benchmark_summary`).
- **`auto_stop_mins`** — bumped from default 10 to 60 to prevent persist
  failures during long Lakebase phases of the harness.
